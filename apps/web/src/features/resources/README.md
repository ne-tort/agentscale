# Resources feature boundary

`ResourceWorkspace` remains the contract-blocked canonical profile/version/materialization surface. The project Resources route now composes a separate doorway over the existing first-party module runtime and ContentOps panel; it does not claim those independent APIs fulfill the canonical resource contract.

## Project module doorway

`ProjectModuleResources` calls the existing authenticated module runtime service and renders only exact bound module IDs `mod_prompts`, `mod_files`, and `mod_mcp` returned for the current project. The current project ID is passed to module list/detail/metadata/data calls. Each visible tile shows API-returned local/global bind and child edit rights. Unbound modules link to the existing module bindings surface; module-list and metadata failures render errors/retry rather than demo data.

The runtime component owns manifest navigation, table rows, project scope pickers, CRUD, declared actions, uploads and row/FileRef mechanics. The prompt module's nested `prompt_files_editor` metadata widget is the only UI extension: when the backend manifest declares `prompt_paths.files_json` and the existing `prompt_path_settings` detail view, a named allowlisted slot presents validated nested name/priority/Markdown editing and writes through `PATCH /projects/{project_id}/runtime-modules/mod_prompts/data/prompt_paths/{row_id}`. The API's PATCH merges provided row fields; this UI sends `files_json` only after re-reading the owner-scoped row and comparing its current files against the editor baseline. The prompt `prompt_files_editor` slot preserves each entry's existing keys and body field, validates the JSON-list shape before edits, and performs a best-effort GET/current-files comparison before `PATCH`. The server has no row version or compare-and-swap token, so concurrent edits in the interval between this check and the PATCH can still overwrite each other; the UI must not describe this as atomic versioning. The project module data route accepts page parameters, but returns complete SoT row arrays (not paginated responses) for these JSON tables. To keep project filters correct across every row without inventing a filtered endpoint, the doorway reads up to 1,000 rows per first-party table, applies project_ids plus manifest context filters, then paginates locally. Over 1,000 rows it shows a visible read error instead of silently presenting an incomplete filtered list. No project module-profile setter is called from this surface because the existing implementation toggles `is_default` on the resolved SoT and can therefore affect other projects on a global bind.

Files and MCP render their backend-declared module forms. File uploads use the existing cabinet content-upload route and canonical FileRefs. Files entries with an asset_id also offer an authenticated exact-version content download through the existing module runtime FileRef API; no storage key is used as authority. Read-only binds disable mutation and upload controls. Resource tiles do not bind/unbind modules; that operation remains in module administration.

## Confirmed routes used by project Resources

- `GET /api/v1/projects/{project_id}/runtime-modules` returns the modules enabled for and bound to the project with bind kind and child edit rights.
- `GET /api/v1/projects/{project_id}/runtime-modules/{module_id}/meta/documents/{slug}` reads each module's declared `tables`, `columns`, `views`, `tabs`, and `actions`.
- `GET /api/v1/projects/{project_id}/runtime-modules/{module_id}/data/{table_slug}` reads rows from the module's resolved project SoT; `POST`, `PATCH`, and `DELETE` on the same data path are guarded by project access, bind state and child edit rights.
- `GET /api/v1/cabinets/{cabinet_id}/modules/{module_id}/bound-projects` supplies project picker choices for metadata-declared project_multiselect fields.
- `POST /api/v1/cabinets/{cabinet_id}/content/upload` uploads module file contents and returns a FileRef. Declared module actions use `POST /api/v1/cabinets/{cabinet_id}/modules/{module_id}/actions/{action_id}/invoke`. Exact FileRef downloads use `GET /api/v1/content/assets/{asset_id}/download?proxy=1&blob_version_id=...` through the existing module runtime adapter.
- The existing authenticated `ContentOpsPanel` still uses company-scoped Content API routes after the project GET confirms matching project ID and company ID. It is separate from module Files/MCP FileRefs.

No browser API for canonical profile snapshots, resource versions/bindings, resource diffs, or atomic materialization plan/apply was found or added. The legacy `PATCH /projects/{project_id}/modules/{module_id}/profile` handler is also deliberately unused here: on a global bind its current implementation changes `is_default` on the resolved shared SoT. The project Resources page keeps all existing `RESOURCE_CONTRACT_BLOCKERS` visible; Assets continue to advertise the Content Service's absent version-history/provenance/workspace-binding capabilities. Product module data editing is not canonical Resource profile editing, and a row/FileRef write does not imply a workspace sync/materialization result.

Acceptance scenarios are authored in the app integration suite. Per migration verification freeze, tests, builds, compile, lint, formatting, git checks and other formal verification commands are intentionally not run.
