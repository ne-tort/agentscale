# Чат: зависание страницы и целевая архитектура рендера

Документ фиксирует разбор инцидента «есть чаты, после открытия которых страница
зависает через пару секунд» и принципы, к которым приведён чат.

## Симптом

Открываешь некоторые чаты — через 1–3 секунды страница перестаёт отвечать.
Визуально почти ничего: иногда мигает индикатор подгрузки блока, иногда нет.
Вкладка жива, но UI не реагирует.

## Причина

Два дефекта, которые усиливают друг друга.

### 1. Автоподгрузка истории без верхней границы

`ChatMessageList._maybeAutoloadOlder()` вызывается из `build` и из
`didUpdateWidget` и грузит предыдущую страницу, **пока контент не заполнит
вьюпорт**:

```dart
final contentFillsViewport = pos.maxScrollExtent > pos.viewportDimension;
if (!contentFillsViewport) widget.onLoadOlder!();
```

Границы у этого цикла не было. Если страница истории не добавляла видимых
блоков (в событиях много служебных: дельты стрима, usage, скрытые мета-события),
то `maxScrollExtent` не рос, и приложение продолжало тянуть страницу за
страницей со скоростью сети. Чат с длинной историей проходил её целиком за
секунды.

### 2. Список без виртуализации

Блоки рендерились через `ListView(children: …)` — Flutter монтировал элементы
для **всех** блоков истории, включая те, что за пределами экрана. Каждая
подгруженная страница увеличивала число элементов, а следующий кадр стоил
пропорционально их количеству. Вместе с п.1 это давало квадратичный рост:
цикл ускорялся ровно тогда, когда список становился дороже.

Плюс на каждом кадре заново считалась группировка блоков (`groupDisplayEntries`
проходит всю историю) и безусловно слался `notifyImmediate()` из поллера хвоста
каждые 2.5 с — даже когда новых событий не было.

## Что исправлено

| Место | Было | Стало |
|---|---|---|
| `_maybeAutoloadOlder` | грузит, пока не заполнит экран — без ограничений | не больше 3 попыток подряд без прироста блоков, дальше пауза до ручного скролла к началу |
| `loadOlderTranscript` | доверял `has_more` от сервера | если страница не дала ни блоков, ни сдвига курсора — `hasMoreHistory=false` (цикл разрывается на первом холостом шаге) |
| вставка страницы | `insertAll(0, …)` без проверки | дедуп по ключу блока: пересекающийся диапазон не раздувает список |
| список | `ListView(children:)` — все элементы смонтированы | `ListView.builder` + `findChildIndexCallback` — элементы только для видимого окна, при подгрузке сверху существующие не пересоздаются |
| группировка | пересчёт на каждый кадр | кэш по отпечатку блоков + флаг стрима |
| поллер хвоста | `notifyImmediate()` всегда | только при реальном изменении (число блоков, хвост, флаг хода) |

Регресс-тесты: `apps/flutter/test/chat_history_loop_test.dart` — 4 теста
(холостая страница останавливает листание, страница с блоками продолжает,
пересечение не даёт дублей, виджет не зацикливает автоподгрузку).

## Принципы, к которым приведён чат

Это устоявшиеся практики чат-клиентов с агентом (Cursor, Claude/DeepSeek-style
харнессы, Telegram-подобные ленты). Формулирую их как правила для нашего кода.

### 1. Виртуализация обязательна

Лента чата — потенциально неограниченный список. Рендерить нужно только видимое
окно. Любая «оптимизация», которая монтирует все сообщения, ломается на первом
же длинном чате, и ломается нелинейно.

### 2. Автоподгрузка — с прогрессом и потолком

Подгрузка «пока не заполнит экран» — законный приём для коротких лент, но она
обязана проверять, что предыдущий шаг что-то дал, и упираться в предел. Правило:

* грузим только при простое (нет запроса в полёте);
* после каждой страницы сравниваем состояние (число блоков / курсор);
* нет прироста N раз подряд → пауза, дальше только по действию пользователя.

### 3. Данные и виджеты кэшируются по отпечатку

Пересчёт группировки, свёрток и «сессий работы» зависит от набора блоков, а не
от кадра. Пересчёт на каждый кадр — скрытая квадратичная сложность: анимация
ховера или скролл заставляют пересчитывать всю историю.

### 4. Обновление UI только по факту изменения

Поток событий от агента идёт часто (дельты стрима) и ещё чаще идёт поллер,
когда стрима нет. Будить UI нужно только при реальной разнице состояния:
сравниваем длину, хвост и флаг «ход в работе». Иначе экран перерисовывается на
пустых ответах, и это видно как «дёргание» на слабых машинах.

### 5. Схлопывание блоков — локальное состояние, не часть модели

Раскрытие/сворачивание tool-блока, спойлера, панели работы — это состояние
конкретного виджета. Оно не должно попадать в модель блоков: иначе каждый
клик инвалидирует кэш отрисовки и перестраивает ленту. В нашем коде это уже так
(`_openSpoilers` внутри состояния блока) — правило зафиксировано, чтобы не
сломать.

### 6. Привязка к низу — по позиции, а не по расчёту высоты

Reverse-список: «низ» — это `pixels ≈ 0`. Привязка «прокрутить к последнему»
должна идти в 0, а не в `maxScrollExtent`: у ленты с переменной высотой extent
оценивается приблизительно, и прыжок в него даёт промахи. Это же снимает
прежнюю причину использовать eager-список.

### 7. Явные состояния загрузки

Три разных состояния не должны выглядеть одинаково: «история ещё грузится»,
«агент работает», «соединение переподключается». В нашем коде они уже разделены
(`loadingHistory`, `turnInProgress`, `showReconnectIndicator`) — правило
сохранено.

## Что осталось за рамками

* **Виртуализация внутри блока.** Раскрытый tool-блок с огромным выводом
  (тысячи строк) по-прежнему рендерится целиком. Следующий шаг — обрезать вывод
  и догружать по кнопке.
* **Замеры.** Полезно добавить в debug-режиме счётчик кадров и числа
  смонтированных блоков, чтобы такие регрессии ловились глазами.
* **Серверный `has_more`.** Клиент теперь защищён и от «врущего» `has_more`, но
  причину стоит искать и на бэкенде: если страница событий не содержит ни одного
  отображаемого блока, это стоит знать в метриках.

## Примечание об исследовании

Задача предполагала разбор устройства чата в DeepSeek Harness и ZCode. В этой
сессии веб-поиск недоступен (нет API-ключа), а DSH поставляется только
скомпилированным `app.asar` без исходников, поэтому прочитать их код не удалось.
Принципы выше сформулированы из общих практик построения чатов с агентом и из
разбора собственного кода; они не являются пересказом конкретных реализаций.
