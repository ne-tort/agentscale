# Принципы as-built документации слоёв

Документация в `12-layer-docs/` — **обязательный артефакт реализации**, не «потом напишем».  
Она должна давать сжатую, точную картину слоя: смысл, устройство, границы, связи.

---

## 1. Три источника — разные роли

| Источник | Вопрос | Менять когда |
|----------|--------|--------------|
| Канон `docs/target/01`…`10` | Каким должен быть продукт? | Меняется продуктовое решение |
| План `11-implementation-plan` | Когда слой считать закрытым? Порядок? | Меняется стратегия поставки |
| **As-built `12-layer-docs`** | Что уже реализовано и как работает? | **Каждый** PR, меняющий слой |

Запрещено подменять канон текстом «как сейчас в коде» в `01`…`10`. Расхождения канон↔код — только в карточке § Gaps.

---

## 2. Обязательные разделы карточки слоя

Каждый `LNN-*.md` **должен** содержать разделы ниже (пустые — с явной пометкой `—` / `n/a`, не удалять заголовки).

### 2.1 Header

| Поле | Смысл |
|------|--------|
| `Status` | `not_started` \| `partial` \| `done` \| `deprecated` |
| `Quality` | целое **0…10** — законченность/качество по [quality-score.md](quality-score.md) |
| `Quality note` | 1–3 предложения обоснования балла |
| `Plan` | Ссылка на `11/.../LNN-*.md` |
| `Canon` | Ссылки на канон `01`…`10` |
| `Last updated` | Дата + краткий ref (PR/commit) |
| `Owners` | Опционально: зона ответственности |


### 2.2 Семантика слоя

Сжато (½–1 экран):

- зачем слой в продукте;
- ключевые сущности и их смысл (не поля БД списком);
- чем слой **не** является (границы).

Читатель после этого раздела понимает роль слоя без кода и без канона целиком.

### 2.3 Что сделано

Маркированный перечень **поставленного** поведения (факт).  
Группировать по возможностям, не по именам файлов.

Для `partial`: явно «сделано» vs «не сделано» (можно таблицей).

### 2.4 Как сделано

Логика реализации без простыни кода:

- основные потоки (mermaid или нумерованные шаги);
- важные решения (почему так; 1–3 предложения);
- где enforcement (authz, validation, isolation);
- runtime topology (процессы, sidecar, схемы БД) — если есть.

Псевдокод — только если без него неочевидно; не копировать классы целиком.

### 2.5 Контракты

| Подраздел | Содержание |
|-----------|------------|
| Публикует | ID из [contracts-index](../11-implementation-plan/contracts-index.md) + краткая форма (endpoint/port/event/widget) |
| Потребляет | ID контрактов соседей |
| Совместимость | Ломающие изменения, version notes |

Если контракт ещё не реализован — статус `planned` в таблице, не молчание.

### 2.6 Связи

- кто вызывает слой / кого вызывает слой;
- данные, которые пересекают границу;
- события in/out.

Сверка с [map.md](map.md): при изменении связей обновить и map.

### 2.7 Инварианты

Жёсткие правила, которые код обязан соблюдать (и тесты ловят).  
Пример: «peer не читает `cab_inst_*` соседа»; «secret не в API response».

### 2.8 Карта кода (навигация)

Только **точки входа** и якоря:

```text
apps/api/.../<module>/          # ответственность одной строкой
apps/flutter/lib/...            #
```

Запрещено: дамп дерева репо, пересказ каждого метода.  
Цель — знать куда смотреть, логику держать в § Как сделано / Семантика.

### 2.9 Gaps vs канон / DoD

Таблица: требование канона или пункт DoD плана → `done` / `partial` / `todo` / `won't` (с причиной).  
Это единственное место, где фиксируется «пока не как в каноне».

### 2.10 Проверка

Как убедиться, что слой жив:

- команды тестов / contract suite;
- ручной smoke (если неизбежен) — 3–5 шагов max.

### 2.11 Оценка качества (0–10)

Обязательно. Рубрика и потолки: [quality-score.md](quality-score.md).

| Ось | Балл 0–2 | Комментарий |
|-----|----------|-------------|
| A. Полнота DoD | | |
| B. Контракты | | |
| C. Инварианты и проверки | | |
| D. As-built ясность | | |
| **Quality (итог 0–10)** | | с учётом потолков |

`Status: done` допустим только при **Quality ≥ 8**.

## 3. Стиль: сжатость и однозначность

| Да | Нет |
|----|-----|
| Имена сущностей из глоссария | Синонимы «пользователь/tenant/орг» вперемешку |
| «Reject если…» | «Желательно проверять…» |
| Актуальный факт | «Когда-нибудь», «возможно» без Gaps |
| Ссылки на C-ID / канон | Копипаста длинных кусков канона |

Объём ориентир: **1–3 экрана** на зрелый слой; больше — дробить подразделы, не размазывать.

---

## 4. Когда обновлять (жёстко)

| Событие | Действие |
|---------|----------|
| PR меняет поведение / контракт / инвариант слоя | Обновить карточку в **том же** PR |
| Закрытие пункта DoD в `11` | Отразить в § Что сделано + Gaps |
| Слой → `done` в checklist-master | `Status: done`, Gaps без критичных `todo`, **Quality ≥ 8** |
| Ломающий контракт | Карточка + [contracts-index](../11-implementation-plan/contracts-index.md) Compatibility log |
| Только рефакторинг без смены поведения | Карта кода (±), Last updated; семантику не раздувать |

**Нельзя** помечать слой `done` в плане `11`, если as-built карточка пустая или `not_started`.

---

## 5. Связь с планом `11`

| `11` | `12` |
|------|------|
| «Не считать готовым, если…» | Должно быть опровергнуто фактом в § Что сделано / Проверка |
| contracts-index | § Контракты карточек = source of truth «что реально торчит» |
| sequence | map.md показывает фактические стрелки после поставки |
| checklist `done` | `Quality ≥ 8` + [quality-score](quality-score.md) |
