# WAVE11 — «Готовые сборки»: динамический каталог ПК/серверов

Статус: **дизайн**. Прод не трогаем — только dev.

Документ распутывает замысел заказчика, переводит его в термины as-built кода и
задаёт целевую модель. Продолжение WAVE10 (`WAVE10-ASSEMBLY.md`).

---

## 1. Что не так с текущим подходом

Сейчас (после WAVE10) сборка существует **только внутри чата и только для одной
позиции заказчика**: `equipment_builds` (`chats: current`) + группы-кандидаты
слотов `found_groups` (`build_id` + `slot_type_id`). Каждую сборку ИИ собирает
**с нуля под каждую заявку**: ищет компоненты в каталоге, записывает группы,
ждёт материализацию офферов.

Следствия:
- одна и та же работа повторяется для каждой похожей заявки;
- нет накопленного знания о совместимости (сокет ↔ плата ↔ ОЗУ) — оно каждый
  раз выводится заново и живёт только в `note` конкретной группы;
- нет возможности «держать витрину» сборок, которая сама обновляется по ценам;
- нельзя сравнить десятки вариантов между собой — их просто нет до заявки.

**Цель WAVE11:** пополняемый каталог готовых сборок, который (а) наполняет ИИ,
(б) привязан к реальной БД партномерами/алиасами/хэшами, (в) сам пересчитывает
цены и состав, (г) копируется в чат под конкретную позицию, где ИИ доводит его
вручную.

## 2. Замысел заказчика → технические термины

| Формулировка | Что это в коде | Уточнение |
|---|---|---|
| «Группы и Готовые сборки внутри этих групп» | `build_groups` → `ready_builds` | Группа = **домен совместимости** (сокет, тип ОЗУ, форм-фактор) + бюджетный класс. Не «папка для удобства», а граница, внутри которой компоненты взаимозаменяемы |
| «В группы добавляется всё совместимое оборудование + делится на классы» | `build_group_items` (пул) с `class_key` | Пул — переиспользуемый набор компонентов группы. Класс (`ssd_256`, `ram_16`, `cpu_6c`) — то, что **не даёт сравнивать несравнимое** |
| «Сборки получают оборудование из своей Группы как сопоставление» | `ready_build_slots.item_id` → пул | Слот сборки ссылается на элемент пула, а не хранит своего поставщика |
| «Динамический партномер/алиас/хэш… выбирается лучшая цена» | `ready_build_slots.mode = dynamic` | Слот resolved в самый дешёвый доступный компонент своего класса; **может дрейфовать** при изменении цен |
| «Либо фиксированный для сборки… чтобы не уехал на альтернативу» | `ready_build_slots.mode = fixed` | Слот закреплён за конкретным компонентом/партномером; цена меняется, состав — нет |
| «Комплектующие — не товары поставщиков, а партномера/алиасы/хэши из БД» | ключи `part_number` / `aliases_pn` / `aliases_hash` | Ровно те же ключи, что в `found_groups`: разрешение в офферы делает OpenSearch, а не ИИ |
| «16 ГБ дешевле 32 ГБ — не значит, что 16 ГБ выигрывает» | ранжирование **внутри** `(group_id, class_signature)` | Разные классы никогда не конкурируют по цене. Это инвариант, а не эвристика |
| «Данные сборки копируются в „Сборку“ чата, дальше ИИ работает с копией» | действие `ready_build_attach` | Каталог = библиотека шаблонов; чат = рабочая копия. Копируются ключи, а не цены |
| «Количество для некоторых типов (2 плашки ОЗУ)» | `qty` на слоте | Свойство **слота**, а не кандидата: у слота может быть несколько альтернатив, количество одно |

### Что я меняю в формулировках заказчика (и почему)

1. **Группа — это домен совместимости, а не тег.** Иначе «группировка по
   бюджетности» позволила бы сравнивать AM4 и LGA1700 сборки, что ломает сам
   смысл автозамены. Бюджетный класс остаётся атрибутом группы, но **поверх**
   сокета.
2. **Класс живёт на элементе пула и в сигнатуре сборки**, а не только в названии.
   Без машиночитаемого `class_key` автоматика не сможет отличить «SSD 256» от
   «SSD 512» и начнёт подставлять cheaper-несовместимое.
3. **Каталог хранит ключи, а не офферы.** Материализация офферов остаётся в чате
   (WAVE10). В каталоге — только резолв «лучшая цена по ключам», иначе сотни
   сборок × десятки офферов дадут взрывной рост строк и дублей.

## 3. Целевая модель данных

```
build_groups (Группы сборок)                    chats: all
├── build_group_items (Пул оборудования)        chats: all
│     ключи: part_number / aliases_pn / aliases_hash
│     класс: type_id + class_key  (ssd_256, ram_16, cpu_6c …)
│     пайплайн: offers_count, best_price, best_seller, in_stock
└── ready_builds (Готовые сборки)               chats: all
      ├── ready_build_slots (Слоты)             chats: all
      │     type_id, qty, mode(dynamic|fixed),
      │     class_key | item_id | собственные ключи
      │     пайплайн: resolved_item_id, resolved_price, line_total
      └── пайплайн: components_count, price_total,
                    price_min/price_max, on_order, is_cheapest_in_class

request_lines (позиция заказчика)               chats: current
└── equipment_builds  ← КОПИЯ через ready_build_attach
      └── found_groups (build_id + slot_type_id)  — механика WAVE10
            └── found_offers → бюджет → закупка
```

### Скоупинг (важно)

Каталог — `chats: all`: строки имеют `session_id = NULL`, видны из любого чата
проекта, `unique`-колонки действуют на весь проект. Читать их нужно обычным
`io.list(...)`, **никогда** `list_project_wide(...)` — тот фильтрует
`session_id IN (...)`, а NULL-строки в такую выборку не попадают.

Рабочая копия — `chats: current` (`equipment_builds`, `found_groups`,
`found_offers`, `budget_lines`): изоляция чата как в WAVE10.

### Сигнатура класса

`class_signature` = нормализованная строка из классовых атрибутов сборки,
например `6c|16gb|ssd256|nogpu`. Ранжирование «самая дешёвая сборка» идёт
**внутри** `(group_id, class_signature)`. Разные сигнатуры = разные витрины,
они не конкурируют. Это прямая реализация требования «16 ГБ не выигрывает у
32 ГБ только потому, что дешевле».

## 4. Динамика: как каталог обновляется сам

Новое действие `ready_builds_sync` (`kind: equipment.ready_builds`):

1. Читает пул и слоты (`chats: all` → `io.list`).
2. **Один батч-запрос** в OpenSearch по всем ключам (переиспользует подход
   `_search_docs`: `terms` по партномерам + `terms` по `src_hash`).
3. На элемент пула: `offers_count`, `best_price`, `best_seller`, `best_title`,
   `in_stock` — с учётом `trusted_sellers` (отключённые исключены,
   приоритетный бьёт цену внутри класса).
4. На слот: `dynamic` → минимум по классу среди доступных; `fixed` → цена
   закреплённого. `line_total = resolved_price × qty`.
5. На сборку: `price_total = Σ line_total`, `price_min`/`price_max` (диапазон
   по альтернативам dynamic-слотов), `match_label`, `on_order`,
   `is_cheapest_in_class`.
6. Пишет **только изменившиеся** поля (guard от write-amplification, как в
   существующем пайплайне — иначе ложный «проект требует обновления»).

**Триггеры:** запись в любую из 4 таблиц каталога + **beat-расписание** (час,
прецедент — `prodavan-equipment-catalog-reindex`). Beat обязателен: требование
«автообновляемая по цене база» не выполняется на одних пользовательских
триггерах — цены меняются в каталоге, а не в наших строках.

## 5. Копирование в чат (`ready_build_attach`)

Вход: `ready_build_id` + `line_id` (позиция заказчика).

1. Создаёт `equipment_builds` в бакете чата: `line_id`, `name`, `build_kind`,
   `source_ready_build_id` (провенанс), `slot_qty` из слотов.
2. Для каждого слота создаёт `found_groups` с `build_id` + `slot_type_id` +
   ключами **разрешённого** компонента (`part_number` / `aliases_pn` /
   `aliases_hash`) и `match_kind`.
3. Дальше работает штатная механика WAVE10: материализация офферов, best,
   цена сборки, бюджет, закупка, UI-выбор альтернатив.

Копируются **ключи**, а не цены: копия сразу начинает жить своей жизнью и
тянет актуальные офферы. ИИ может в копии: заменить слот на другой
партномер, добавить алиас/хэш найденного товара, перевести dynamic → fixed
(через `slot_mode`), поменять `qty`.

Обратная синхронизация (чат → каталог) **не** делается намеренно: копия
принадлежит заявке, каталог — витрина. Перенос решения в каталог — отдельное
осознанное действие ИИ (`ready_build_upsert`), не автоматика.

---

## 6. Количество (qty) — требование 1

`qty` — свойство **слота**, а не кандидата: у слота несколько альтернатив, но
«2 плашки ОЗУ» верно для любой из них.

- Каталог: колонка `qty` в `ready_build_slots` (число, ≥1, дефолт 1).
- Чат: `equipment_builds.slot_qty = {type_id: qty}` — **параллельная** карта к
  существующей `slots = {type_id: group_id}`. Не ломает данные и UI WAVE10
  (вариант «вложить qty внутрь slots» потребовал бы миграции всех существующих
  сборок и переделки pick-логики).
- Цена: `total += slot_price × qty` — и в каталоге, и в чате.
- UI: количество редактируется на строке слота; в pick-списке кандидатов не
  показывается (оно не про кандидата).

## 7. MCP-инструменты

Поверх существующих 15 инструментов `prodavan-equipment` — 5 новых
(намеренно мало: у агента уже есть generic `module_data_*`, дублировать CRUD
для каждой таблицы не нужно, а раздувание списка инструментов жжёт контекст).

| Инструмент | Зачем |
|---|---|
| `ready_builds_catalog` | **Единственная точка чтения каталога** с уровнями компактности: `scope=groups\|items\|builds\|build`, фильтры (`group_id`, `type_id`, `class_key`, `build_kind`, `budget_tier`), `detail=compact\|full`. Без него generic-list вернул бы сотни полных тел и съел контекст |
| `build_group_upsert` | Группа: домен совместимости + бюджетный класс |
| `build_group_item_upsert` | Элемент пула: валидирует ключи (хотя бы один из pn/aliases/hash) и `class_key` |
| `ready_build_upsert` | Сборка **вместе со слотами одним вызовом** (вложенный массив): ИИ создаёт сборку за один ход, а не за N |
| `ready_build_attach` | Копирование сборки в чат на позицию заказчика |

Удаление — generic `module_data_delete` + каскад (`cascade_equipment_delete`):
группа → её пул и сборки; сборка → её слоты.

`ready_builds_catalog` — ключевой инструмент: требование «получать каталог с
различными видами компактности» буквально про него.

## 8. UI

- **Управление → Подбор техники → «Готовые сборки»** (новый пункт хаба
  `equipment_hub_management`): список групп → сборки группы → слоты сборки.
- Колонки сборок: класс, компонентов, цена (и диапазон, если dynamic-слоты
  дают вилку), наличие, «дешевлейшая в классе».
- Слоты: тип, класс, режим (dynamic/fixed), qty, разрешённый компонент, цена,
  alternatives.
- Действие «В чат» на сборке → `ready_build_attach` (выбор позиции).
- Данные чата (WAVE10) не меняются визуально, кроме qty на слоте.

## 9. Промпты

Новый файл правил `70-ready-builds.md` + правка `AGENTS.md` и `60-builds.md`:

- **Приоритет потока:** сначала поиск в каталоге готовых сборок
  (`ready_builds_catalog`), и только если подходящей нет — сборка с нуля.
  Это главная поведенческая замена WAVE10.
- Как выбирать группу/класс под заявку (по сокету, бюджету, классовым атрибутам).
- Когда `fixed`, а когда `dynamic` (фиксировать то, что критично заказчику или
  что уже согласовано; остальное — dynamic, пусть экономит).
- `qty` — про количество, а не про альтернативы.
- `ready_build_attach` → дальше работа с копией в чате.
- Наполнение каталога — отдельная задача («сделай 20 сборок AM4 DDR4 от
  бюджетных до средних»), не побочный продукт заявки.

## 10. План по фазам

**Фаза 1 — qty (независимо от каталога).** `equipment_builds.slot_qty`,
`total += price × qty` в `_sync_builds`, UI-редактор количества,
`_recomputeBuildTotals` во Flutter, тесты. Полезно сразу и в текущей модели.

**Фаза 2 — схема каталога.** 4 таблицы `chats: all`, колонки, виды, пункт хаба
«Готовые сборки», миграция.

**Фаза 3 — пайплайн каталога.** Батч-резолв цен из OpenSearch, разрешение
dynamic/fixed слотов, итоги сборок, `is_cheapest_in_class`, beat-триггер,
guard от write-amplification, тесты.

**Фаза 4 — MCP + промпты.** 5 инструментов, каскад удалений, `ready_build_attach`,
`70-ready-builds.md`, правка `AGENTS.md`/`60-builds.md`, bump версии пакета.

**Фаза 5 — проверка.** Юнит-тесты, сквозной прогон через ИИ-агента на dev
(наполнение каталога → attach к позиции → бюджет), документация.

## 11. Риски и как их закрываем

| Риск | Мера |
|---|---|
| Взрывной рост строк (сотни сборок × офферы) | Каталог хранит **ключи и лучшую цену**, не офферы; офферы материализуются только в чате после attach |
| Нагрузка на OpenSearch | Один батч-запрос на прогон (как `_search_docs`), а не запрос на компонент |
| Write-amplification → ложный «проект требует обновления» | Писать только изменённые поля; `synced_at` обновлять только вместе с реальным изменением |
| Дрейф dynamic-слота на несовместимое | Резолв строго внутри `(group_id, class_key)`; группа задаёт сокет/тип ОЗУ |
| Несравнимое сравнивается по цене | Ранжирование только внутри `(group_id, class_signature)` |
| Agent тонет в контексте при чтении каталога | `ready_builds_catalog` с `detail=compact` и фильтрами вместо generic-list |
| Протухшие цены в каталоге | Beat-расписание (час) + триггеры на запись + кнопка «Обновить цены» |
| `chats: all` строки невидимы для `list_project_wide` | Каталог читаем только `io.list`; зафиксировано в доке и коде |

### Смена провайдера проекта: цепочка из четырёх дефектов

Прогон упёрся в то, что агент в одном из проектов вообще не отвечал
(`503 PROVIDER_MODEL_ERROR · 401 Invalid token`) при свежем списке моделей.
Разбор дал четыре независимых дефекта, каждый из которых по отдельности
ломал доставку обновлений до живого пода:

| # | Дефект | Фикс |
|---|---|---|
| 9 | `PATCH /projects/{id}` со сменой провайдера был голой записью в БД: `.prodavan/config.yaml` в поде и снапшоты ACTIVE-сессий оставались прежними, а `/models/live` резолвил всё заново — отсюда «витрина новая, вызов 401» | #191 |
| 10 | `force_rehydrate` в `sync_desired` ничего не форсил: `_prepare_reload` вызывался только при `reason == "reload"`. В sandbox-режиме гидрация живого пода заблокирована маркером `.hydrated`, а API-сторона гидрацию не делает вовсе — любой rematerialize был no-op'ом | #191 |
| 11 | Воркер Celery не поднимал Redis → `bump_pod_bridge_generation` в strict-режиме ронял джобу `rematerialize_project`; заодно `run_with_job_lock` молча работал без блокировки | #194 |
